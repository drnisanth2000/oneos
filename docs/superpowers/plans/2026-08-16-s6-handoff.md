## Method — do not vary it

Per task: RED first, capture the failure output → GREEN → full suite → an
**independent reviewer subagent** → fix every Critical and Important →
re-review until clean → commit staging exactly the task's files plus a ledger
entry → push → next task. One committed, reviewed task before the next begins.

Models: implementation on Sonnet, review on Opus. The evidence for the split is
in the ledger — implementations have been faithful; verification has been the
weak point regardless of model.

## The lesson this branch has paid for seven times

Across five reviewed tasks, **nearly every finding was a defect in the tests,
not the feature.** Recurring shapes:

- A test that passes with the code under test deleted. One monkeypatched a
  function and never called it; one asserted `hasattr` on a frozen dataclass;
  one asserted a count of zero that an absent file also returns.
- A test proving a mechanism with the one input shape the codebase never
  produces — an AST trigger that fired zero times while its test passed.
- A ledger claiming something is pinned when it is not. **Twice.**
- A test calling a handler *function* directly with a synthetic scope, so
  unregistering the production wiring left every test green.
- A requirement with no test at all — "the fallback never returns 200" was
  unguarded while the fallback did exactly that.

**Countermeasure: mutation, not inspection.** For every behavioural test, break
the implementation, confirm that test fails, restore, confirm byte-identity.
Report it. "The suite is green" is evidence only after something was broken and
the suite went red.
