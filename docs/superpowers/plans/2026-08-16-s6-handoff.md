## OPEN DECISION — resolve before Task 11 writes code

Task 10 implemented and escalated a conflict it could not resolve alone. It is
the first thing the next session must settle, and it needs a human ruling
because it touches the design's regression table.

**The conflict.** `@console_route(surface="fragment-only")` makes `is_fragment`
return True unconditionally, and `status_for` returns **200** for any
refusal-severity code on a fragment. `tests/test_app.py:393
test_tampered_proposal_form_writes_nothing` asserts `status_code >= 400` in six
parametrized cases — and it is **not** among the two tests the design's
regression table permits to change.

Task 10 therefore left the five `fragment-only` handlers undecorated
(`propose`, `outbox_approve`, `outbox_reject`, `registry_delete_preview`,
`registry_delete_execute`), verifying experimentally that decorating `propose`
now flips all six cases to 200. That deviates from the plan's Task 10 table,
which lists them.

**Why it cannot simply be deferred.** Task 11 must decorate `propose` and give
it a route-level catch. At that point the tampered form becomes a described
refusal rendered into `#diff-{index}` at 200 — so the test breaks then instead.
Moving the decoration does not avoid the collision; it relocates it.

**What the test actually asserts.** Its substance is a **state proof** — `HEAD`
unchanged, entity bytes unchanged, no proposal written — plus one status
expectation. The design's regression rule says tests whose subject is a refusal
decision, an isolation guarantee, or a state proof "remain unchanged **in
substance**", and separately that "a route test's status or markup expectation
may change where S6 deliberately alters presentation, and every such test is
listed above." This test is not listed. So either the table is genuinely
incomplete for the third time, or the renderer is wrong to make a tampered form
a 200 refusal.

**Do not resolve this by relaxing the assertion.** Three scope breaches on this
branch each arrived labelled "bounded". If the ruling is that the table needs a
third entry, amend the **design** first — it is normative — then the plan, then
the test, in that order and in separate commits.

A review was dispatched to rule on it; its verdict may already be recorded in
the ledger. Check the ledger's Task 10 entry before deciding.

## The lesson this branch has paid for four times

Across four reviewed tasks, **nearly every finding was a defect in the tests,
not the feature.** Recurring shapes:

- A test that passes with the code under test deleted. One monkeypatched a
  function and never called it; one asserted `hasattr` on a frozen dataclass;
  one asserted a count of zero that an absent file also returns.
- A test proving a mechanism with the one input shape the codebase never
  produces — an AST trigger that fired zero times while its test passed.
- A ledger claiming something is pinned when it is not. **Twice.**

**Countermeasure: mutation, not inspection.** For every behavioural test, break
the implementation, confirm that test fails, restore, confirm byte-identity.
Report it. "The suite is green" is evidence only after something was broken and
the suite went red.
